## Claude Code 的 ~/.claude/skills/文件夹结构

Skills 是 Claude Code 的"技能包"系统，每个 skill 本质上是 **一个独立的文件夹** ，放在以下两个位置之一：

| 作用域 | 路径 | 说明 |
| --- | --- | --- |
| **个人级** （跨项目通用） | `~/.claude/skills/` | 不在 git 里，只你本人可见 |
| **项目级** （团队协作） | `<项目根>/.claude/skills/` | 随仓库提交，团队共享 |

---

### 单个 Skill 文件夹的标准结构

```
纯文本~/.claude/skills/
└── my-skill/                      ← 文件夹名 = skill ID（kebab-case）
    ├── SKILL.md                   ← ✅【必需】核心文件，Claude 读的就是它
    ├── README.md                  ← 可选，给人看的说明文档
    ├── scripts/                   ← 可选，可执行脚本
    │   ├── setup.sh
    │   ├── helper.py
    │   └── validate.js
    ├── references/ 或 resources/ ← 可选，参考资料/静态数据
    │   ├── REFERENCE.md
    │   ├── schema.json
    │   └── glossary.csv
    ├── templates/                 ← 可选，输出模板
    │   └── report_format.md
    ├── assets/                     ← 可选，静态资源（图标、模板文件等）
    └── docs/                       ← 可选，附加文档
```

**记住一条铁律： `SKILL.md` 是唯一必需的文件** ，其他都是按需增删的。

## 先把决策框架钉死（按这个走就不会乱）

### 第 0 层（永远加载）：SKILL.md的 YAML frontmatter

- •
	**放什么** ： `name` 、 `description` （必要时 `when_to_use` ）、 `allowed-tools` 等 **发现与调度元数据**
- •
	**判据** ：只要它是 Skill，就必须有；而且 `description` 要写得足够"可检索"（Claude 靠它选 Skill）

### 第 1 层（匹配后才读）：SKILL.md的正文 Markdown

- •
	**放什么** ：工作流步骤、规则、决策树、关键约束、少量示例
- •
	**放它 ≠ 拆出去的条件** ：
	- •
		正文内容 **≤ ~几百行** （官方给的经验值是"争取 < 500 行"比较舒服）
		- •
		且内容是 **流程指令** ，不是"大部头参考资料"
- •
	**一旦正文开始臃肿、或里面有"章节"可被独立按需读** ，就该拆

### 第 2 层（真正"可选"的那些子文件/子目录）：只在需要时才被 Claude 读到或执行

拆出去的唯一理由是： **不拆就会让 SKILL.md 变胖、token 变贵、结构变难维护** 。

## 逐个说：每个可选目录/文件，什么时候要、什么时候不要

### 1) scripts/（最容易误用）

放 **可执行脚本** ：shell、Python、Node… Claude 通过 `Bash` 去 *执行* 它们，而不是把它们全文当文本读进上下文。

**要 `scripts/` 当且仅当你需要：**

- •
	有 **确定性的机械计算/转换/校验** ，LLM 自己拼命令不稳定
	例：解析二进制/Office/PDF、批量 rename、schema validate、调用 CLI 工具链
- •
	需要 **依赖 pip/npm 能装的库** （pandas、pdfplumber 之类）
- •
	你想把"复杂实现"锁死在一个文件里，避免 LLM 每次自由发挥出错

**不要放 `scripts/` 当：**

- •
	只是"写几行说明"——那属于 SKILL.md 正文
- •
	你在放 **密钥/secrets** 、构建产物、 `__pycache__` 、 `node_modules` （这些不该进 skill 目录）
- •
	你的公司环境不允许 Claude 执行本地脚本（那就只能走纯 prompt 指令路线）

> 安全点写法：配合 `allowed-tools: [Bash]` + 只让你信任的脚本路径可执行，别给开放式 "跑任意命令" 的自由。

---

### 2) references/（或你叫 docs/、rfc/、api/……）

放 **大部头"只读参考资料"** （Markdown/JSON Schema/SQL DDL/协议说明），给 Claude **按链接去读** ，而不是硬塞进正文。

**要它就当：**

- •
	你有字段语义表、错误码表、API 参数表、数据字典、合规条文 → 这些一拆出去，SKILL.md 立刻清爽
- •
	并且你在 SKILL.md 里明确写："需要 XXX 时，先读 `references/xxx.md` "

**不要它就当：**

- •
	其实只有一小段规则——直接写在 SKILL.md 里更可命中、更好调试

---

### 3) examples/（或就 EXAMPLES.md/ examples.md）

**专门放"样本输入输出、gold standard 对照"。**

**要它就当：**

- •
	你要给 Claude 一个"照这个格式/照这个决策"的强暗示
- •
	样例一旦多了（>2–3 个），散在正文会淹没有效指令 → 拆
- •
	样例文件可能是带格式的样本（`.md` /`.json` /甚至小 `.csv` ），更适合当独立文件引用

**不要它就当：**

- •
	只有 1 个短例子 → 内联在正文中反而更稳定（少一次"没读到引用"的风险）

---

### 4) templates/（或 assets/里放模板）

**放"产出物骨架/格式契约"** ：PR 模板、MR 描述模板、release note 骨架、report markdown layout、JSON 输出 schema 示例等。

**要它就当：**

- •
	Skill 的产出强调一致性/机器可读性/团队规范（比"自由发挥格式"更重要）
- •
	并且模板本身是"给你复制填充"的东西，不是长篇讲解

**不要它就当：**

- •
	格式规则三句话能写完 → 正文里用代码 fence 写死就行

---

### 5) 你可能见到的 schemas// assets// tests/

这些不是官方硬性约定名，更多是 **作者自选型** ：

- •
	`schemas/` ：如果你想放 JSON Schema / OpenAPI 片段供校验或生成 → 合理
- •
	`assets/` ：静态资源（图标、样板文件、sample fixture）→ 合理但要警惕体积
- •
	`tests/` ：手工样本输入 → 可以，但别把 CI 产物放进来

官方文档给出的 canonical 示例形态主要是： **`SKILL.md` +（可选） `template.md` / `examples/` / `scripts/`** ，其余名字你按团队可读性取名就行，关键是"SKILL.md 里显式引用到"。

## 一个最实用的"要不要拆"速判表

| 你想放的东西 | 应该放哪 | 信号：该拆出去了吗？ |
| --- | --- | --- |
| 触发元数据 | `SKILL.md` frontmatter | — |
| 步骤指令 / 规则 / 约束 | `SKILL.md` 正文 | 正文明显过长、章节可独立读 |
| 大表 / 字段词典 / API 细节 | `references/xxx.md` | 一拆就让正文从"文档"变回"指令" |
| 样本 IO / 对照格式 | `examples/` | 样例 ≥3 或占行数太多 |
| 产出格式骨架 | `templates/` | 模板 >10 行或需要版本化 |
| 要真正跑代码/CLI | `scripts/` | 你发现 LLM "拼命令"不稳定/不可审计 |
| 要校验结构 | `schemas/` | 你希望拿 schema 做 gate |

## 什么时候才需要 skills/xxx/template/？

**只有当模板是"纯 Skill 私有的胶水材料"** ，且与知识库生命周期无关时，才值得放 skills 下，例如：

- •
	一段固定输出骨架（JSON schema / 报告壳子），你根本想让它跟着 skill 一起分发
- •
	Skill 是给别人用的，你不指望对方 Vault 里有对应模板

但你这种场景—— **Obsidian 笔记模板是知识库一等公民** ——放 Vault 的 `Templates/` 才是正解，把模板扣出来塞进 skills 纯粹是自找割裂。

简短结论： **optional 的那些子目录并不是"必须放在 skills 文件夹里才能工作"** 。

真正"必须"的只有一个： **`SKILL.md` 本身要在 skills 目录里** （个人级 `~/.claude/skills/<skill-id>/SKILL.md` 或项目级 `.claude/skills/<skill-id>/SKILL.md` ），这样 Claude Code 才能发现并加载这个 skill。

除此之外， `SKILL.md` 里面的指令完全可以写： **去读 / 去执行 / 去复制** 你 vault 里任何合理路径的文件——模板、参考文档、样例、甚至是脚本——所以很多 optional 资产 **确实可以不塞进 `skills/xxx/` 里** 。

但要分两类看，不然容易踩坑👇

## 1) 哪些是"更适合放 vault（知识库）"的 —— 你基本都能挪出去

- •
	**templates/** （笔记模板、frontmatter 骨架、输出格式壳子）
	✅ 放 `Templates/` 、 `Assets/` 、 `_system/templates/` 这类 vault 路径更合理（Obsidian 可直接管理、链接、版本、预览）。SKILL.md 里只写一句："从 `Templates/meeting.md` 读取模板内容，然后填参写入目标路径"。
- •
	**references/** （字段词典、术语表、规范条文、API 片段、决策对照表）
	✅ 也可以做成 vault 里的 `References/` 、 `Meta/` 、 `Docs/` ——尤其当它本身就是你知识库的一部分、会被人手动翻阅或被其它笔记引用时。
- •
	**examples/** （样本笔记/样本输出）
	✅ 若样本本质是"笔记长得什么样"的示范，放 vault 的模板/示例区更自然；skill 里写"参考 `Examples/...`"。

> 这些挪出去后， **skill 更像"一个流程 + 指向资产的指针"，而不是把所有资产打包进自己的口袋** ——对你的 Obsidian 场景反而更健康。

---

## 2) 但有一类要谨慎：scripts/（真正会被执行的代码）

严格说也能放 vault，但我 **不建议** 把 vault 的常规文档区变成"运行时脚本目录"：

- •
	Obsidian 可能会把它当成普通文件索引（取决于你的排除规则）
- •
	更容易出现误提交/误同步/执行权限混乱
- •
	你可能在 `allowed-tools: [Bash]` 里给了"跑东西"的能力，路径越零散越难审

更稳妥的做法通常是二选一：

- •
	**仍放在 skills 旁** ： `~/.claude/skills/<skill>/scripts/check.sh` （私有、跟 skill 走、不污染 vault）
- •
	**或放到 vault 外的工具位** ：比如 `~/bin/` 、 `~/tools/` 、项目里专门的 `scripts/` （非笔记区），然后在 SKILL.md 里写 **固定相对/绝对路径 + 只允许指定脚本名** （别写"随便 bash 任何命令"那种宽松描述）

如果你的脚本只是"读文件/写文件/简单文本处理"，很多时候你甚至 **不需要真放脚本** ：SKILL.md 直接让 Claude 用文件读写工具把模板渲染出来就够了（更安全、更少执行面）。

## 3) 给你一条好用的分界线（决定放哪的口诀）

> **skill 管"流程与约定"，vault 管"内容与模板"。**
> 
> `skills/xxx/` 放的是"这个 skill 的定义与机制"；凡是你觉得"这明明是我的 vault 资产，不该被绑死在 skills 文件夹里"，就放 vault；SKILL.md 用路径引用它。

所以回到你的问题： **是的，前面那些 optional 目录对应的资产大多可以不放 skills 下** ；但别理解为"skills 文件夹就没意义了"——它的意义就在于"让 SKILL.md 可被发现 + 成为一个稳定的锚点"，锚点之外，资源放哪由归属权决定。
