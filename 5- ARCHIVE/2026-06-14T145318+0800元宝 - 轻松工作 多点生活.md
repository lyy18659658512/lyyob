## 🧠 一句话理解

传统做法是：把所有工具的说明文档全部塞进 System Prompt → **上下文爆炸、变贵、变"笨"** 。

渐进式设计的做法是：像查手册一样——

- •
	**先看目录** （有哪些技能）
- •
	**再翻章节** （这个技能怎么用）
- •
	**最后查附录** （详细参考资料/脚本/模板）

只加载"当下需要的那一层"。

---

## 🏗️ 三层渐进式加载（核心骨架）

| 层级 | 内容 | 什么时候在上下文里 | 占 Token |
| --- | --- | --- | --- |
| **L1 · 元数据层** | `name` + `description` （一句话说明"我是谁、我干嘛用"） | ✅ **常驻** （启动时就读） | ~几十~百来 Token/Skill |
| **L2 · 指令层** | `SKILL.md` 正文：执行步骤、决策规则、边界条件、最佳实践 | ❌ **按需** ：任务匹配后才加载 | 几百~几千 Tokens |
| **L3 · 资源层** | `scripts/` 、 `references/` 、 `assets/` （代码、API 文档、模板等） | ❌ **更按需** ：执行阶段才读取/调用 | 不限大小，但不占主上下文 |

### 工作流程长这样：

1. 1.
	**启动** ：Agent 只读所有 Skill 的 L1 元数据（很轻），建一个"能力索引"
2. 2.
	**用户说话** ：Agent 扫描元数据的 `description` ，判断"哪个 Skill 可能对得上"
3. 3.
	**命中** ：才加载那个 Skill 的 `SKILL.md` （L2），得到完整操作手册
4. 4.
	**执行中** ：如果指令里引用了脚本或参考文档（L3），再按需读取

本质上就是： **路由靠 L1，执行靠 L2，重型支撑靠 L3。**

## 🎯 它解决什么痛点？

| 痛点 | 渐进式设计怎么解 |
| --- | --- |
| **上下文窗口有限** | 99% 的 Skill 内容不在上下文里待命，省出大量 Token 给真实任务 |
| **Token 成本暴涨** | 只加载命中的那一个/几个 Skill，而不是 N 个 × 完整文档 |
| **任务干扰 / "降智"** | 无关 Skill 的规则不在场，减少噪声和冲突 |
| **技能越多越难管** | 可以挂几十上百个 Skill，元数据加起来也就一两千 Token |

## 🔑 所以"渐进式设计"的本质

它不是说 Skill 要"一步步教你用"，而是说：

> **Skill 的知识要按"信息密度 × 使用时机"分层封装，让 Agent 的上下文永远只装"当前任务真正要用的那一块"。**
