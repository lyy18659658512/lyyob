# 知识库操作规范

## 📁 文件夹结构

```
0 - INBOX           ← 外部收集（剪藏/WeRead/对话导出），每周清理
1 - JOURNAL         ← 时间线
  └── YYYY-MM/        ← 按月份归档
      └── YYYY-MM-DD.md
2 - ACTION          ← 行动
  ├── 1-Career/      ← 事业、副业、教学
  ├── 2-Learning/    ← 课程、读书、技能学习
  ├── 3-Life/        ← 财务、健康、日常
  └── 9-someday/     ← 孵化池
3 - KNOWLEDGE       ← 知识沉淀
  ├── 1-Literature    ← 外部来源笔记
  │   ├── 1-Books
  │   ├── 2-Courses
  │   ├── 3-Articles
  │   └── 4-LLM
  └── 2-Atomic       ← 提炼的概念卡片
5- ARCHIVE          ← 已完成/过期的内容
6 - ATTACHMENTS     ← 图片/素材附件
7 - RESOURCE        ← 资源文件
9 - SYSTEM          ← 配置
  ├── Templates
  └── 知识库操作规范.md
```

## 📋 YAML Frontmatter 规范

所有笔记通用字段：
```yaml
---
title: ""
type: ""       # 见下方 type 列表
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []       # 见下方 tags 字段使用规则
---
```

### type 值列表
- `diary` - 日记
- `project` - 项目
- `book` - 读书笔记
- `article` - 文章笔记
- `llm` - LLM 问答笔记
- `course` - 课程笔记
- `atomic` - 原子笔记
- `dashboard` - 仪表盘/首页
- `system` - 系统文档

### links 字段使用规则

`links` **主要用于连接 2 - ACTION 与 3 - KNOWLEDGE 两个领域。** 每一条 links 都代表一次"行动产生了知识"或"知识驱动了行动"的真实事件。

同一领域内的链接（ACTION↔ACTION、KNOWLEDGE↔KNOWLEDGE）除非是强逻辑关系（因果、继承、同主题），否则优先用正文链接。

**links 中的 wikilink 只写笔记名，不含路径。** 即使不同文件夹有同名笔记，Obsidian「最短路径」机制在底层记录完整链路，展示层只需 `[[笔记名]]` 即可正确跳转，无需手动加文件夹前缀。

### source 字段使用规则

`source` **仅用于原子笔记，标识提炼出处。** 每一条 source 代表"这篇原子概念是从哪来的"。

| 场景 | `source` 填写 | `links` 填写 |
|------|--------------|-------------|
| 从某篇文献笔记提炼而来 | `"[[文献笔记名]]"` | 按需填使用到的项目 |
| 从多篇文献综合提炼 | `["[[文献A]]", "[[文献B]]"]` | 按需填使用到的项目 |
| 由项目实施产生 | 留空 `""` | `"[[项目笔记]]"` |
| 个人实践/纯洞察（无文献无项目） | 留空 `""` | 留空 `""` |

> `source` 和 `links` 都是可选字段。原子笔记可以全部留空（纯个人洞察），没有问题。

**与其他字段的分工：**

| 关系类型 | 用什么 | 说明 |
|---------|--------|------|
| 原子笔记 → 文献笔记（提炼出处） | `source` | 仅在原子笔记中填写，文献笔记不反向填 |
| KNOWLEDGE ↔ ACTION（项目关联） | `links` | 双向填写，见上方 links 规则 |
| 原子笔记 ↔ 原子笔记（概念关联） | 正文 `[[wikilink]]` | 在内容中用 wiki 链接表达派生或关联 |

`[[wikilink]]` **使用建议：以 inline 为主，栏目为辅。**

- **Inline 是首选**：写作时自然提到某个概念，当场用 `[[wikilink]]` 链过去。链接在上下文中才有意义——读者看到"这个概念与 [[双向链接]] 一致"就知道为什么要看那边。
- **栏目只做补充**：写完后扫一眼，如果有正文没写到的关联笔记，在末尾加轻量栏目做补充；没有遗漏就不加。

```
写作时自然提到 → 当场 [[wikilink]]（inline）
                    ↓
写完后扫一眼 → 还有关联但正文没提到 → 末尾补充栏目（可选）
                    ↓
                没有遗漏 → 不用加栏目
```

> 一篇笔记应当能独立读懂，链接是锦上添花，不为了链而链。

### tags 字段使用规则

**tags 只写主题，不写类型。**

| 该不该写 | 例子 | 理由 |
|---------|------|------|
| ❌ 不写文件夹已有信息 | `book`、`course`、`project` | type 字段和文件夹已表达 |
| ❌ 不写单篇笔记特有词 | 仅一篇笔记用到的专有名词 | 用搜索找更快 |
| ✅ 写跨领域的主题词 | `AI` 可能出现在课程、项目、原子笔记中 | 跨笔记聚合，这是 tag 的核心价值 |
| ✅ 写概念/领域关键词 | `学习`、`Agent`、`数学` | 方便按主题筛选 |

> 注：此规则为初始版本，后续可根据实际使用补充或改进。

## 🔄 日常使用流程

### 随时
- 有想法 → 写入 1 - JOURNAL
- 读书/上课/问AI → 直接写入 3 - KNOWLEDGE

### 每周（可选）
- 清理 INBOX，分发到对应文件夹
- 从文献笔记提炼原子笔记，建立链接

### 项目结束时
- 相关项目笔记移入 5- ARCHIVE

## 📖 微信读书笔记工作流

使用 `weread-book-note` skill 自动处理。

**触发方式**：对 Claude 说"整理读书笔记"、"更新读书笔记"、"处理微信读书笔记"等。

### 输出
- 路径：`3 - KNOWLEDGE/1-Literature/1-Books/{书名}.md`
- 模板：[[9 - SYSTEM/Templates/读书笔记模板]]

### 字段归属规则

| 来源 | 字段 | 说明 |
|------|------|------|
| **WeRead 自动抓取** | `title` `author` `progress` | 每次新建/更新都从源文件同步 |
| **系统自动生成** | `type` → 固定 `book` | 新建时设定 |
| | `created` → 首次创建日期 | 后续更新永不修改 |
| | `updated` → 处理当天日期 | 有新增内容时刷新 |
| **手动维护** | `tags` `links` | 更新时原样保留，**永不覆盖** |
| **正文占位符** | `## 📝 摘录与思考` `## 💡 关键收获` | 需手动补充，不会被自动填充 |

### 源文件处理

- INBOX 源文件在处理成功后**自动删除**，不保留备份
- 增量更新仅追加新 refID，已有摘录不受影响
- 若 WeRead 导出的 `progress` 变更，笔记中的进度会同步更新

## 💬 AI 对话日志工作流

使用 `conversation-log` skill 自动处理。

**触发方式**：对 Claude 说"保存这段对话"、"把对话整理成笔记"、"把聊天记录结构化"等。

### 输出
- 路径：`3 - KNOWLEDGE/1-Literature/4-LLM/{对话主题}.md`
- 模板：[[对话日志模板]]

### 字段归属规则

| 来源 | 字段 | 说明 |
|------|------|------|
| **技能自动填充** | `type` → 固定 `llm` | 新建时设定 |
| | `model` → AI 模型名称 | 从对话来源推断 |
| | `created` → 首次创建日期 | 后续更新永不修改 |
| | `updated` → 处理当天日期 | 有新增内容时刷新 |
| **手动维护** | `tags` `aliases` | 更新时原样保留，**永不覆盖** |
| **正文占位符** | `## 对话背景` `## 精选对话记录` `## 关键信息点` | 需手动审核后确认 |

### 源文件处理

- INBOX 中的第三方 AI 对话导出（如元宝、ChatGPT）→ 处理后**移入 5- ARCHIVE**（保留原始记录备查，不删除）
- JSON 会话文件（`.claudian/sessions/`）→ 保留在原位置，不移入 ARCHIVE

## 💡 原则

- 文件夹管类型，标签管主题
- INBOX 不是必经之路，而是兜底方案
- 知识类笔记永不归档，时效性内容才移入 ARCHIVE
- 无需背负回顾压力，顺其自然

## 🤖 一致性检测

进行系统级变更后，可让 AI 自动执行一致性检测：

### 检测命令

> **"帮我做知识库一致性检测"**
> **"检查模板和文档是否同步"**
> **"运行一致性检测"**
> **"知识库体检"**
>
> > 💡 以上命令会触发专门的 `consistency-check` Skill 执行完整检测

### AI 会检测的内容

1. **模板 vs 操作规范**
   - `9 - SYSTEM/Templates/` 下每个模板的 YAML 字段 → 与操作规范中 `各类型专属字段` 逐行比对
   - 是否存在模板有但规范未记录的字段
   - 是否存在规范有但模板未包含的字段
   - 模板列表是否与 `可用模板列表` 一致

2. **模板 vs CLAUDE.md**
   - type 与模板的映射关系是否一致
   - 模板是否在 CLAUDE.md 中有对应的 entry

3. **Skill vs 模板**
   - Skill 中硬编码的模板路径是否有效
   - Skill 硬编码的 YAML 字段是否与模板一致

4. **变更记录完整性**
   - 最近的系统变更是否已在 [[变更记录]] 中记录

### 检测结果处理

- AI 会生成差异报告，标记每项为 `✅ 一致` / `⚠️ 不一致`
- 如有不一致，可指示 AI 直接修复，或手动修复后重新检测
